## Notes

- **IP convention:** every guest uses a static `192.168.2.<VMID>` address (last octet = VMID). On 2026-06-17 the `work` (100), `work2` (103), and `rag` (107) containers were re-IP'd via `pct set <id> -net0 …` to bring them in line (`.23→.100`, `.25→.103`, `.28→.107`). VM 109 (Main) was brought in line the same day (`.20→.109`) via a router DHCP reservation pinned to its MAC, applied by bouncing its NetworkManager connection (`nmcli con down/up netplan-enp6s18`); the host runs DHCP-assigned networking, so the reservation — not a guest static config — fixes the address.
- LXC rows (IPs, status, tags) were verified live against `pct list` / `pct config` on 2026-06-17. VM 109 (Main)'s `.109` IP was verified live from the host itself (this workstation *is* VM 109); its status is carried over from the previous snapshot.
- Container **108 / terraCT** was destroyed on 2026-06-17 (`pct destroy 108` on the node). It was the container `terraform/lxc/` was templated for; the repo's Terraform now manages no live guests.
- Container **104 / Frigate** was destroyed on 2026-06-17 (`pct stop 104` + `pct destroy 104`); its 64G rootfs (`vm-104-disk-0`) was removed. Freed IP `192.168.2.26`.
- Containers 111, 200, 201 carry a `terraform` tag but are not in this repo's state — likely managed elsewhere or imported separately.
- **Host RGB / OpenRGB (2026-06-23):** The ASUS **Aura** USB controller (`0b05:19af`) was removed from VM 109's USB passthrough so the **host** can drive it. OpenRGB now runs as a host systemd service (`openrgb.service`) serving `192.168.2.70:6742`, controlling all 3 RGB controllers (2× ENE DRAM over SMBus + Aura motherboard). Do not re-pass `0b05:19af` to a VM. See [OPENRGB_SERVER_SETUP.md](OPENRGB_SERVER_SETUP.md). 109's remaining USB passthroughs (`13d3:3571`, `047d:8188`, `1bcf:2284`, `25a7:fa61`) are unaffected.
- **VM 109 USB — physical controller passthrough (2026-07-22):** to fix a webcam-triggered display freeze (Logitech **MX Brio 4K**, `046d:0944`), the physical USB controller **`0c:00.0`** (ASMedia `1022:43f7`, own IOMMU group 33) was passed through to VM 109 as `hostpci2` — replacing the emulated USB device-redirection for the Brio + the two dongles on that controller (`046d:0944`, `047d:8188`, `25a7:fa61`, i.e. old `usb2`/`usb13`/`usb9`, now removed). Bluetooth (`13d3:3571`) and UGREEN cam (`1bcf:2284`) stay as device-redirection. **Do not add `1022:43f7` to `vfio.conf` by ID** — `0c:00.0` and the Aura's controller `0e:00.0` share that ID; address-based `hostpci` only. Full write-up: [Incident/proxmox-vm109-gpu-freeze-incident.md](Incident/proxmox-vm109-gpu-freeze-incident.md) (Mode C).
- **VM 109 GPU all-functions passthrough (2026-07-22):** `hostpci0` changed from `0000:08:00.0` to `0000:08:00` so the guest also receives the GTX 1660 SUPER's HDMI/DP audio function (`08:00.1`) for monitor-speaker audio, plus its (unused) USB-C controller and UCSI. Each function has its own IOMMU group; applies on next QEMU restart. Complete peripheral map: [109_PERIPHERAL_PASSTHROUGH.md](109_PERIPHERAL_PASSTHROUGH.md).
- **VM 109 won't start after host reboot — `i2c_nvidia_gpu` blacklisted (2026-07-22 evening):** after a full PVE host reboot, VM 109's boot-time autostart `qm start 109` hung in an unkillable kernel `D` state unbinding the GPU's USB-C/UCSI function **`08:00.3`** (`10de:1aed`) from the host **`i2c_nvidia_gpu`** driver (`i2c_del_adapter` deadlock), holding the VM lock so every restart failed with `can't lock file … got timeout`. **Fix:** added `blacklist i2c_nvidia_gpu` + `blacklist i2c_ccgx_ucsi` to `/etc/modprobe.d/vfio.conf` (backup `vfio.conf.bak.20260722`), `update-initramfs -u -k all`, host reboot — now `vfio-pci` claims `08:00.3` cleanly at boot with nothing to unbind. This is **not** `blacklist nvidia` (that causes host boot hangs); the tiny UCSI helper is safe to blacklist and does not affect the RTX 3060 used by LXC 107. Full write-up: [Incident/proxmox-vm109-gpu-freeze-incident.md](Incident/proxmox-vm109-gpu-freeze-incident.md) (Mode D).
- **VM 109 USB — Mode C reverted to device-redirection (2026-07-22 evening):** the whole-controller passthrough of `0c:00.0` (`hostpci2`) was **undone** — the passed-through controller made the **mouse intermittently stick**. Keyboard/mouse dongles (`047d:8188` Kensington, `25a7:fa61` Compx) and the **MX Brio** (`046d:0944`) are back on per-device **USB redirection** (`usb2`/`usb4`/`usb3`). `hostpci2` was removed and `0c:00.0` rebound live to the host `xhci_hcd` (`echo 0000:0c:00.0 > /sys/bus/pci/drivers/vfio-pci/unbind` → `… > /sys/bus/pci/drivers_probe`) so the host re-enumerates the devices for the forwards; this is the default at boot now that `hostpci2` is gone (`0c:00.0` is not in `vfio.conf`). Current 109 USB map: `usb1`=BT `13d3:3571`, `usb2`=Kensington `047d:8188`, `usb3`=Brio `046d:0944`, `usb4`=Compx `25a7:fa61`, `usb5`=UGREEN `1bcf:2284`. Physical layout settled 2026-07-22 to reduce input jitter: Brio isolated on `0c:00.0`, keyboard/mouse on CPU controllers (`10:00.3` Kensington, `10:00.4` Compx + UGREEN) — redirection matches by device ID so ports can move freely; see [109_PERIPHERAL_PASSTHROUGH.md](109_PERIPHERAL_PASSTHROUGH.md#physical-controller-layout). ⚠️ The **Brio on redirection re-exposes the Mode C freeze risk** under heavy 4K/UVC capture. Definitive stable config: **1920×1080 @ 30 fps, MJPEG, on a USB 2.0 port, redirected** (`usb3`); higher resolutions **green-screen**. USB 3.0 is *worse* (redirection → 352×288; `0c:00.0` controller passthrough → Brio reset-loops, tried & reverted 2026-07-22). Keep the Brio on a USB 2.0 (black USB-A) port; don't chase >1080p. See [109_PERIPHERAL_PASSTHROUGH.md](109_PERIPHERAL_PASSTHROUGH.md) / incident doc "Brio resolution ceiling". Full write-up: [Incident/proxmox-vm109-gpu-freeze-incident.md](Incident/proxmox-vm109-gpu-freeze-incident.md) (Mode C revert).
- ⛔ **VM 109 — CPU xHCI passthrough is HOST-FATAL (2026-07-24, Mode E):** passing the AMD Raphael CPU USB controller **`10:00.4`** (`1022:15b7`) as `hostpci2` **hard-reset the entire Proxmox host the moment VM 109 started**, then crash-looped the host on every boot (~60 s each) while autostart retried the VM — journal tails were misleading because the reset lost the final log lines. Reverted same day (`qm set 109 --delete hostpci2`; `usb3` Brio forward restored). **Never pass `10:00.3`/`10:00.4` to any guest** (their advertised `pm` reset is broken in hardware; `10:00.6` audio passthrough is unaffected). If a PVE boot crash-loop ever recurs mid-`startall`: SSH in within ~60 s and kill `startall` / set the suspect VM `--onboot 0`. Full write-up: [Incident/proxmox-vm109-gpu-freeze-incident.md](Incident/proxmox-vm109-gpu-freeze-incident.md) (Mode E).
- **VM 109 / LXC 205 webcams — Brio refunded, C922 + UGREEN split (2026-07-24 evening):** the **MX Brio was returned for refund** (its SuperSpeed modes were unreachable on this box: SS-over-redirection delivers 0 frames, chipset controller passthrough corrupts (Mode C), CPU xHCI passthrough is host-fatal (Mode E)). Replacement **Logitech C922 Pro Stream** (`046d:085c`, native USB 2.0, 1080p30/720p60 MJPEG) is on VM 109 `usb3` — verified: video streams and the **mic is clean under sustained 1080p load** (no Brio-style iso-contention clicks); low light halves fps via auto-exposure. The **UGREEN 2K cam** (`1bcf:2284`) moved from VM 109 to **LXC 205 (knowledge-lab)**: host `uvcvideo` owns it, `/dev/video0`+`/dev/video1` device-passed as `dev5`/`dev6` (`mode=0666`, alongside the nvidia `dev0`–`dev4`; entries hotplug into the running CT; host video indices renumber on replug — recheck paths then). VM 109 USB map now: `usb1`=BT, `usb2`=Kensington keyboard, `usb3`=C922, `usb4`=Compx mouse. Details: [109_PERIPHERAL_PASSTHROUGH.md](109_PERIPHERAL_PASSTHROUGH.md).
- **4 TB NVMe added → PCI renumbering blocked VM 109 (2026-08-04):** installing a Seagate FireCuda/E18 4 TB NVMe (now `nvme1n1`, unformatted) put its controller on **bus `10:00`**, shifting the AMD Raphael complex `10:00.x` → **`11:00.x`**. VM 109 then failed to start: `no PCI device found for '0000:10:00.6'` (its `hostpci1` audio). Fix: `qm set 109 -hostpci1 0000:11:00.6,pcie=1`. The GPU stayed at `08:00` (unchanged). ⚠️ **Address-based `hostpci` entries break whenever PCIe devices are added/removed** — after any hardware change, re-locate passthrough devices by ID (`lspci -nn -d 1022:15e3` etc.) before starting VMs. The Mode E forbidden Raphael xHCIs are likewise now at `11:00.3`/`11:00.4` (IDs `1022:15b6`/`15b7`) — their old `10:00.3`/`.4` addresses now belong to the new SSD.
- ⛔ **Thin-pool 100% full outage (2026-08-02/03):** `pve/data` (794 G) filled to 100% (`lvs` attr `twi-aotzD-`) — guest writes returned EIO for days ("potential data loss" in host kernel log), CTs 100/103/107/203 failed to mount at boot, and **VM 109's root fs was corrupted so the guest wouldn't boot** while `qm status` said "running" (`vga: none` = no virtual console — check agent/ping, then offline `e2fsck` via `losetup -fP`). Recovery: `pct fstrim` on every CT freed ~460 GiB (→ 91.6%), `e2fsck -fy` on VM 109's root, then next-day repair of zero-filled files inside the guest (`libssl.so.3` → broke sudo/DNS/services; Firefox binary; dpkg's `openssl.list`) using **`qm guest exec 109` as the root channel**. Root cause: nothing ever trims (PVE never does it automatically) and the VG has only 16 G free so the pool can't autoextend. **Watch `lvs pve/data`; Data% ≥ 95% is an outage in progress.** Also fixed alongside: nginx boot-race drop-in (`nginx.service.d/wait-for-pve.conf`, the Jul 24 attempt had silently written a 0-byte file), CT 205's ALSA card renumbering breaking its autostart (mic dev paths moved card 0→2; failure shows only in the startall task, not `systemctl --failed`). Full write-up: [Incident/proxmox-thinpool-full-incident.md](Incident/proxmox-thinpool-full-incident.md).
- **Storage migration → 4 TB SSD (2026-08-04, the durable capacity fix):** the new **`nvme4tb-lvm`** pool was created on the FireCuda 530 and **all 12 guests were relocated off `local-lvm`** onto it, dropping `pve/data` from **92.4% → ~0%**. CTs moved offline (`pct move-volume <id> rootfs nvme4tb-lvm --delete 1` — stop/move/start, file-level rsync, stayed thin); VM 109 (`scsi0`, 256 G) and VM 204 (`scsi0`, 56 G) moved **online with zero downtime** (`qm disk move … --delete 1`). CT 100's move was blocked by two stale snapshots (`test_snap` 2025-02, `new` 2025-09) — deleted (`pct delsnapshot`) then moved. **Gotcha:** the online-mirrored VM disks land **thick** (Data% 100%) on the target and in-guest `fstrim` does **not** reclaim them despite correct discard config (guest DISC-MAX 1 G, QEMU `discard=unmap`+`detect-zeroes=unmap`, pool `passdown`); to re-thin, do an *offline* `qm disk move` round-trip. Not worth it at 22% pool / ~3 TB free. `local-lvm` is now free to rebalance a couple of guests back onto the faster Gen5 if desired (see performance note: Gen5 seq ≈1.85× Gen4, but random/QD1 — what VMs actually do — is a tie).
- **VM 109 webcam final state — Brio 500 sole camera (2026-07-25):** the interim **C922** was removed from VM 109 and unplugged (kept as a known-good USB2 spare; re-add via `qm set 109 -usb3 host=046d:085c`). Its replacement **Logitech Brio 500** (`046d:0943`, native USB 2.0 over USB-C, `usb5`) is the sole VM camera — verified sustained **1080p30 MJPEG at 29.8 fps even in dim light** (RightLight 4) with a **clean 48 kHz mic under load**. Root cause of the brief two-camera era ending: **all VM 109 USB forwards share one emulated 480 Mbps controller — two simultaneous 1080p streams truncate MJPEG frames (green image) and starve YUYV (flicker)**, verified with OBS holding both cameras 2026-07-25; one camera + mic at 1080p30 MJPEG is clean, two cameras require both at 720p. YUYV above ~480p is never viable on the emulated bus. VM 109 USB map now: `usb1`=BT, `usb2`=Kensington keyboard, `usb4`=Compx mouse, `usb5`=Brio 500. Details: [109_PERIPHERAL_PASSTHROUGH.md](109_PERIPHERAL_PASSTHROUGH.md).
